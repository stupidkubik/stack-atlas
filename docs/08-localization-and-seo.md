# PkgCompass: локализация, маршруты и SEO

Дата: 5 октября 2026. Статус: рабочая спецификация до реализации. Английский v1 и правила индексации из [ADR 0002](decisions/0002-pre-code-decisions.md) приняты; публичные пути, языковой префикс и завершающий slash приняты в [ADR 0008](decisions/0008-public-urls.md). Остальные параметры и способы реализации требуют проверки прототипом.

Основание: [продукт](02-product-and-scope.md), [сценарии](03-user-flows-and-pages.md), [контентная модель](04-content-model.md), [архитектура](05-architecture.md), [качество](11-quality-plan.md). Документ задаёт ожидаемое поведение; сайт, метаданные и проверки ещё не реализованы.

## 1. Идентичность и единый построитель URL

Активные локали v1: `['en']`. Каждый опубликованный редакционный документ имеет явную `locale: 'en'`; публичный HTML — `lang="en"`. В интерфейсе нет переключателя языков и ссылок на ещё не опубликованные переводы.

Актуальный scope — [ADR 0013](decisions/0013-marketing-v1-and-simple-pipeline.md), включая форму и измерение.

Принятая форма URL: `/en/`, `/en/categories/{categorySlug}/`, `/en/libraries/{routeSlug}/`, `/en/compare/{firstSlug}-vs-{secondSlug}/`, `/en/methodology/ai-readiness/`, `/en/request-shortlist/`, `/en/privacy/`. Все публичные HTML-маршруты заканчиваются `/`; технические ресурсы `/robots.txt` и `/sitemap.xml` — нет. `/` постоянно перенаправляется на `/en/` с 308. Автоопределение языка по cookie/IP/Accept-Language в v1 не требуется.

Стабильный ID CMS-продукта, `routeSlug` и `packageName` — разные поля. `@vendor/sdk` остаётся npm-именем и не становится вложенным URL. Переименование SDK не меняет адрес CMS. Slug проверяется на уникальность в соответствующем типе маршрута; рабочий формат — строчные ASCII-буквы/цифры с одиночными дефисами. Для slug библиотеки дополнительно резервируем разделитель `-vs-`, чтобы адрес пары разбирался однозначно. Внешние данные не задают slug автоматически.

Идентичность сравнения — два различных стабильных ID в детерминированном порядке (лексикографически по строкам ID без locale-dependent collation). Порядок slug в адресе соответствует этому порядку ID, а не алфавиту названий. `displayOrder` задаёт порядок колонок и не влияет на URL. Пара B/A перенаправляется 308 на A/B. Адрес существует только для разрешённой пары одной категории; произвольная комбинация не создаёт страницу автоматически.

URL строится одной функцией по сущности и локали. Она используется ссылками, sitemap, canonical, OG и redirect registry; шаблоны строк в отдельных компонентах недопустимы. Абсолютные SEO-адреса используют проверенный production origin из конфигурации, а не входящий Host и не адрес preview deployment. Домен пока не приобретён; примеры в тестах используют тестовый origin.

## 2. Матрица публичных ответов

`index` означает разрешение индексации, а не гарантию попадания в поиск. Canonical — абсолютный URL. Один источник решения о publication readiness должен управлять маршрутом, навигацией и sitemap.

| Маршрут/состояние | HTTP | Canonical | Robots | Sitemap |
| --- | --- | --- | --- | --- |
| Готовая главная `/en/` | 200 | На себя | `index,follow` | Да |
| Готовая категория, библиотека, методология | 200 | На себя | `index,follow` | Да |
| Готовая форма request-shortlist | 200 | На себя | `index,follow` | Да |
| Privacy page | 200 | На себя | `noindex,follow` | Нет |
| Готовое редакционное сравнение | 200 | Каноническая пара | `index,follow` | Да |
| Поиск или фильтрация каталога | 200 | Нормализованный URL этого состояния | `noindex,follow` | Нет |
| Готовое сравнение с indexingRequested=false | 200 | На себя | `noindex,follow` | Нет |
| Неизвестная сущность, непубличный черновик, неразрешённая пара, одинаковые участники | 404 | Отсутствует | `noindex` | Нет |
| Неактивная локаль или отсутствующий опубликованный перевод | 404 | Отсутствует | `noindex` | Нет |
| Старый slug, обратная пара, отсутствующий завершающий `/` | 308 | В ответе redirect не требуется; Location ведёт к актуальной странице | Не требуется | Нет |
| Параметры отслеживания без изменения контента | 200 | Чистый базовый URL | Как у базовой страницы | Только базовый URL |
| Авторизованный preview | 200 | Не генерируем | `noindex,nofollow` | Нет |
| Preview без действующего доступа | 401/403 | Отсутствует | `noindex` в заголовке | Нет |
| Нет доступного контента из-за отказа CMS и нет валидного кеша | 503 | Не объявляем ошибку канонической страницей | Не требуется | Не генерируем ложную пустую карту |

404 отображает полезную английскую страницу с навигацией и реальный статус 404; пустая поисковая выдача — 200. Не перенаправляем неизвестные сущности на главную: это скрывает ошибки ссылок. Отказ источника метрик не меняет статус готового редакционного материала: страница остаётся 200 и объясняет состояние данных.

Неготовое сравнение, включая прямую API-публикацию без трёх критериев/вывода, возвращает404. Публичной draft-оболочки нет. Опубликованные, но не прошедшие минимальную готовность библиотеки/категории также исключаются из публичной выдачи; preview позволяет исправить их.

## 3. Query, canonical и редиректы

Поиск/фильтры применяются только к маршрутам каталога, перечисленным в [сценариях](03-user-flows-and-pages.md). Их имена, значения и правило множественных значений задаёт тот контракт. Параметры v1: `q`, повторяемые `hosting=cloud|self_hosted`, `api=rest|graphql`; внутри фильтра OR, между фильтрами AND. Сортировка фиксированная по displayName; query сортировки в v1 нет. Этот документ не вводит второй словарь параметров. Правило SEO применяется к нормализованному состоянию: любое непустое `q` или действующий фильтр делает страницу `noindex`. Канонический URL сохраняет значимые параметры этого состояния; не утверждаем, что отфильтрованное содержимое идентично полной категории.

Нормализация удаляет пустые/default значения, повторяющиеся значения множественного фильтра, неизвестные параметры и значения вне allowlist; сортирует ключи и значения множественных фильтров; нормализует пробелы запроса по контракту поиска. После этого результат повторной нормализации тот же. Некорректное пользовательское значение не вызывает 500: UI использует допустимое состояние, а нормализованный адрес восстанавливается согласно сценариям. Query не допускается превращать в HTML без экранирования.

`utm_*`, `gclid` и сходные параметры не меняют содержимое и исключаются из canonical. В ядре их наличие не запускает аналитику и не требует хранения атрибуции. Если они пришли вместе с фильтром, canonical сохраняет только значимую часть, а `noindex` остаётся. На detail-страницах query не меняет редакционный документ; параметры preview обрабатываются отдельным защищённым серверным потоком, не как публичный фильтр.

Смена slug требует записи старого пути до публикации нового. Обновляются входящие внутренние ссылки, sitemap и адреса всех затронутых сравнений. Registry хранит old path → stable entity/current path; не допускаются циклы, коллизии, открытые редиректы на произвольный внешний URL и многозвенные цепочки. Старый и обратный URL сводятся одним 308 к финальному пути. Снятие публикации цели делает alias недоступным: 404, а не redirect на draft. Slug нельзя повторно выдать другой сущности, пока существуют alias.

Публичные `noindex`-страницы не блокируем в robots.txt: поисковику требуется прочитать директиву. Canonical и `noindex` имеют разные цели; canonical остаётся сигналом выбора URL, не защитой доступа. Основание: [Google: noindex](https://developers.google.com/search/docs/crawling-indexing/block-indexing), [canonical](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls).

## 4. Готовность к публикации и метаданные

Минимум для индексируемой страницы: опубликованный документ `en`, валидные ссылки/ID/slug, уникальный title, понятное описание, видимый H1, содержательный основной текст. Для библиотеки/сравнения/методологии также обязательны источники и дата редакционной проверки; для home/catalog/form — соответствующий опубликованный либо фиксированный UI-текст и рабочие переходы. Для библиотеки обязательны назначение, применимость, ограничения и объяснимые альтернативы. Для сравнения — опубликованные участники одной категории, критерии, реальные различия и собственный вывод; таблица метрик без редакционного материала недостаточна.

AI-балл не является условием индексации библиотеки: `score: null` при неполной проверке или неприменимости пакета допустим, если состояние понятно. Не выдаём частичный результат за ноль, рейтинг пользователей или научно измеренную эффективность. Формула и версия `cms-ai-support-v1` видны на странице методологии; последний завершённый снимок показывается отдельно с его датой.

Title и description задаёт локализованный материал с безопасными шаблонными defaults; не создаём механически одинаковые описания для всех пар. Числовая метрика не вставляется в title, если её ежедневное изменение не несёт редакционной пользы. OG использует то же название, описание и canonical; отсутствие изображения не блокирует публикацию, при наличии нужны доступный абсолютный URL и корректный alt. Главный контент, метаданные и ссылки доступны в серверном HTML и не зависят от запуска аналитики. Форма имеет собственные title/H1/описание обещания и privacy link; состояние accepted не создаёт отдельный индексируемый URL. API leads/revalidate не входят в sitemap, responses no-store.

Публикация обновляет страницу, метаданные, nav/sitemap и readiness зависимых сравнений. При снятии публикации участника сравнение перестаёт быть индексируемым и удаляется из sitemap. Предложенные в архитектуре условия: резервный TTL 3600 секунд и видимость публикации до 60 секунд после успешного webhook при повторном запросе. Это критерии прототипа, не SLA; уже открытый браузер не обновляется автоматически. Снятие публикации и rename требуют немедленного истечения соответствующего кеша; ограниченный SWR допускается для метрик. Конкретный API выбирается вместе с версией фреймворка и проверяется на реальном окружении. Редакторская валидация Studio помогает, но сервер всё равно проверяет готовность: прямой API-путь не должен обходить правило.

## 5. Sitemap, robots и окружения

`/sitemap.xml` перечисляет только production HTTPS canonical с 200 и готовностью к индексации: без query, alias, drafts, неготовых сравнений и preview host. В v1 небольшой набор допускает один sitemap. `lastmod` отражает фактическое изменение видимого материала/данных этой страницы; не подставляем время сборки для всех записей. Изменение метрик может менять lastmod страницы, если эти метрики действительно видимы; отказ без изменения страницы не обновляет дату.

`/robots.txt` ссылается на production sitemap, разрешает обход публичных страниц, необходимых для чтения `noindex`. Staging/preview deployment закрывается механизмом доступа; `X-Robots-Tag: noindex` — дополнительная защита. Если deploy protection недоступна в выбранной конфигурации, доступ защищается приложением до вывода draft. Проверка отсутствия draft в HTML, API, sitemap, OG и общем кеше обязательна.

Sitemap строится из опубликованной проекции того же read layer, что обслуживает страницы. При сбое CMS сохраняем последний валидный результат либо возвращаем 503, но не заменяем sitemap успешной пустой картой. Fallback: последняя валидная карта из server cache при наличии, иначе503; не отправляем200 с пустым списком из-за технического отказа. [Google: sitemap и значимость lastmod](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap).

## 6. Структурированные данные

Рабочий минимальный набор — `WebSite` на главной, `CollectionPage`/`ItemList` для готовой категории, `BreadcrumbList` для вложенных страниц, `Article` для сравнения и методологии с видимым авторством. Библиотека может описывать CMS через `SoftwareApplication` как `mainEntity` страницы, только когда конкретные свойства соответствуют CMS-продукту; сведения SDK не переносятся на продукт без проверки. Общий `WebPage` допустим, если специализированный тип вводит ложные предположения.

`@id` использует устойчивые production URL/fragment, `url` совпадает с canonical; название, описание, автор, даты и предмет совпадают с видимым материалом. `dateModified` статьи — дата редакционной правки, а дата метрик подписывается отдельно. Не придумываем `offers`, цену, отзывы, `aggregateRating` и не помещаем AI-readiness в пользовательский рейтинг. Не добавляем SearchAction при отсутствии подходящего рабочего поиска и не считаем его условием v1.

Проверки: JSON корректно разбирается; сериализация не позволяет закрыть script тег текстом CMS; поля соответствуют выбранному Schema.org-типу и содержимому. Rich Results Test применяем только к поддерживаемым Google типам; отсутствие rich-result eligibility у базового типа не делает его ошибкой. Даже валидная разметка не обещает расширенный результат. [Google policies](https://developers.google.com/search/docs/appearance/structured-data/sd-policies), [SoftwareApplication](https://schema.org/SoftwareApplication), [Article](https://schema.org/Article).

## 7. Контракт будущих переводов

Новая локаль активируется после перевода интерфейса и проверки publication readiness документов. Stable product ID, связи пакетов и метрики общие; `libraryContent`/`categoryContent`/`comparisonContent`/`page`, заголовки и SEO имеют собственную локаль. Slug продукта и категории остаётся общим по контракту модели; локализованные slug потребуют отдельного пересмотра маршрутизации. CMS-запись с локалью не означает готовность перевода.

Нет опубликованного перевода → 404 по URL этой локали. Можно предложить явную ссылку «Read in English», но нельзя вернуть английский документ 200 под `/de/...` или объявить его немецким. Переключатель содержит только опубликованные версии текущей сущности; перевод главной не означает наличие перевода любой detail-страницы.

При появлении реальных альтернатив генерируем взаимные абсолютные `hreflang`-ссылки, включая self, только между готовыми индексируемыми переводами одной сущности. Canonical каждой полноценной версии ведёт на себя. В v1 hreflang между переводами отсутствует; `x-default` не придумываем без отдельного выбранного fallback. Основание: [Google: localized versions](https://developers.google.com/search/docs/specialty/international/localized-versions).

## 8. Приёмка и зависимости

URL/query-контракт определён. SITE_URL локально — test origin, до release — фактический production Vercel URL или домен; покупка домена не обязательна. Public/preview read layer реализуется в прототипе. До выпуска проверяем всю матрицу на тестовом наборе: reverse pair, slug rename, query/default/UTM, absent locale, draft, failed CMS и снятие публикации. В серверном HTML проверяем title, canonical, robots, lang и JSON-LD; sitemap сверяем со списком индексируемых страниц. Защита preview проверяется в двух независимых сессиях с прогретым кешем. Выполненные проверки и их артефакты записываются по [плану качества](11-quality-plan.md); сейчас это условия приёмки, не отчёт о прохождении.
