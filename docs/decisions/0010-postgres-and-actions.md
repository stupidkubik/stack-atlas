# 0010. PostgreSQL и GitHub Actions — S7, B + A

> Историческая запись: частично заменена [ADR 0013](0013-marketing-v1-and-simple-pipeline.md). Sanity+PostgreSQL+Actions сохранены; требования ledger/receipts/pointers, attempt/hash conflicts, отдельного review writer и reconciliation заменены ограниченным single-writer pipeline. При конфликте применять актуальные спецификации 02–12.

Дата: 5 октября 2026. Статус: принято владельцем проекта.

## Контекст и варианты

Хранение: A — всё в Sanity, B — Sanity и PostgreSQL, C — Sanity и файловый архив. Запуск: A — TypeScript CLI в GitHub Actions, B — Vercel Cron/Functions, C — отдельный worker. Владелец принял B + A: структурированную основу с БД сразу, с учётом дальнейшего развития и подписки.

## Решение

| Sanity | PostgreSQL |
| --- | --- |
| Продукты, категории, пакеты/репозитории и подтверждённый mapping | История метрик и AI-снимков, доказательства эффективной проверки |
| Локализованный редакционный контент, сравнения, страницы и настройки | Журнал запусков, receipts доставки, исключения ошибочных снимков |
| Источники и редакционные подтверждения официальности | Указатели последних попыток, валидных результатов и полного AI-снимка |
| Drafts, публикация и redirects | Долговременное операционное состояние импорта |

Коллектор читает подтверждённый mapping из Sanity и пишет результаты в PostgreSQL. TypeScript CLI запускается локально, по расписанию и вручную через GitHub Actions. Посещение сайта не запускает сбор. Публичный read layer объединяет опубликованный контент Sanity и данные PostgreSQL по стабильному ID продукта.

## Согласованность и восстановление

- Снимок хранит `mappingRevision`, идентичность источника, версии детектора/методологии, даты и hash. История прежнего SDK не отображается как метрики нового SDK.
- Snapshot, receipt и pointers одного продукта фиксируются одной транзакцией PostgreSQL. Повтор доставки того же attempt/hash безопасен; другой hash — конфликт. Старый run не откатывает указатель.
- Распределённую транзакцию Sanity ↔ PostgreSQL не предполагаем. Review в Sanity создаёт новый AI-снимок через проверяемый идемпотентный шаг; pending/failure виден, прежний снимок не редактируется. Доставка review-события и reconciliation уточняются прототипом.
- После записи БД обновление кеша идёт отдельным защищённым серверным путём; неуспех повторяется. Sanity webhook обслуживает редакционную публикацию, а не является единственным источником уведомлений об импорте.
- При отказе БД сохраняем доступный редакционный контент и объясняем недоступность метрик; валидный кеш допускается с исходной датой. Отказ Sanity без доступного контента не маскируется ложным 404.
- Доступы web-read, collector-write, review-write и migrations разделены. Секреты БД не попадают в браузер. CI и preview не пишут production.
- Backup/restore покрывает оба хранилища: стабильные ID, mapping revisions и связи должны согласовываться. Один экспорт Sanity больше не является полным backup проекта.

Структурированный процесс: seed → dry-run → collect/validate → transactional commit → report → resume/retry. Maintenance выполняет проверенный экспорт и безопасную очистку отдельно от обычного сбора.

## Что пока открыто

Провайдер PostgreSQL, план/стоимость, регион, connection pooling, SQL tooling/миграции, backup и изоляция окружений выбираются до реализации storage adapter. Ежедневные метрики, еженедельный AI, история 180 дней и параметры retry/freshness остаются рабочими значениями для проверки, не автоматически утверждёнными этим ADR.

Квоты Sanity теперь рассчитываются для редакционного контента; история БД оценивается отдельно по строкам, объёму, индексам и запросам. Предыдущая рекомендация хранить snapshots/run/pointers в Sanity заменена этим ADR; её расчёты document caps не применяются к PostgreSQL. Прежние ADR сохраняют исторический контекст.
