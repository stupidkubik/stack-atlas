# План реализации: заявка, consent и измерение

Дата: 5 октября 2026. Статус всех задач: запланировано. Код, credentials, аккаунты и проверки этим документом не создаются и не объявляются выполненными. План детализирует только lead/form/consent/measurement поток; нормативные контракты остаются в [сценариях](../03-user-flows-and-pages.md), [архитектуре](../05-architecture.md), [форме](../09-lead-form.md), [измерении](../10-measurement.md), [приёмке](../11-quality-plan.md), [эксплуатации](../12-operations.md) и [ADR 0013](../decisions/0013-marketing-v1-and-simple-pipeline.md).

Предлагаемые ниже пути кода и имена миграций — целевые ориентиры, а не существующие файлы или выбранные номера версий. Сообщения интерфейса остаются на английском по 03. Форма — запрос владельцу о помощи для одного сценария: email, `scenario`, обязательное отдельное разрешение связаться по этому запросу. Analytics consent независим: заявку можно отправить без PostHog. Конверсия возникает только после подтверждённой CRM-записи; операционные количества заявок и consented analytics funnel имеют разные знаменатели.

В v1 входят Brevo Contacts API, PostHog Cloud EU, форма `Request a CMS shortlist`, приватное состояние заявки и его retention/delete/restore, а также consent-only типизированные события и dashboard. Это не подписка: не добавлять newsletter, DOI, автоматические письма/кампании, подтверждение адреса, A/B, общий worker/outbox или дополнительные воронки. Ручной ответ владельца остаётся за пределами приложения.

## Зависимости и порядок

- **Foundation:** `FP-01` нужен для приложения и среды исполнения; `FP-02` — для конфигурации, интерфейсов adapters и полностью offline fixtures; `FP-03` — для migration runner и основы SQL-ролей. Lead schema принадлежит этому плану: фундаментальный migration runner не должен предвосхищать или дублировать её таблицы. После lead/content схем FP-03 применяет точечные grants и проверяет запреты.
- **Live targets:** `FP-04` настраивает отдельные development Brevo list/PostHog EU project и проверяет реальные credentials/лимиты. Его подготовка может идти параллельно с `LM-01`–`LM-03`; live smoke ждёт готовности FP-04. Production targets задаются в release плане и не нужны для прототипа.
- **Независимый lead-прототип:** `LM-01`–`LM-08` собирают работающий вертикальный путь на fake adapters и dev targets, включая прямой URL формы и собственное минимальное подключение consent. Они не зависят от готовности всех шаблонов CW и завершаются до общего `FP-05`; поэтому не возникает цикла `LM` → `CW-07` → `FP-05` → `LM`. Позднее CTA и privacy settings подключаются к общим элементам CW, а `FP-05` проверяет combined flow формы с CMS/collector.
- **Финальная эксплуатация:** `LM-09` готовится после схемы и adapters, но retention/delete/restore rehearsal выполняется совместно с `QA-04`; production release зависит от общей матрицы `Q01–Q19` и `QA-05`. `QA-02` владеет общей сквозной приёмкой, этот план задаёт её lead/measurement evidence.
- **Параллельная работа:** consent manager может разрабатываться после `FP-02` одновременно с SQL/CRM задачами; `LM-07` связывает его с типизированной схемой событий и ответом API. UI формы зависит от API контракта, но визуально может работать с fake adapter до live Brevo.

### LM-01 — Закрепить доменные интерфейсы, target selection и безопасные fixtures

1. Выделить чистые доменные типы `Scenario`, `ContactPermission`, `LeadSubmission`, `LeadResult`, `ConsentState` и event envelopes. Домен не импортирует Next.js, PostgreSQL, Brevo, PostHog или env; сетевые клиенты доступны только через server/client adapters.
2. В конфигурации связать один `APP_ENV` с согласованной парой DB/CRM/analytics targets. Проверять нужные credentials на старте соответствующего server component. Ошибка/пустая dev-конфигурация завершается безопасно и не переключается на production.
3. Зафиксировать имена и границы конфигурации по 05 §4: `SITE_URL`, `APP_ENV`, `PRIVACY_CONTACT_EMAIL`, `DATABASE_LEAD_URL`, `DATABASE_MIGRATION_URL`, `LEAD_HMAC_SECRET`, `BREVO_API_KEY`, `BREVO_REQUEST_LIST_ID`, `NEXT_PUBLIC_POSTHOG_KEY`, `NEXT_PUBLIC_POSTHOG_HOST`. PostHog public key/host доступны клиенту только в EU project; все прочие значения, включая Brevo key и HMAC secret, остаются server-only. В `.env.example` — только имена и пояснение назначения.
4. Вынести fake CRM и stub analytics в FP-02 fixtures. Сценарии фикстур: 2xx upsert, уже существующий контакт, 429, 5xx, auth/config error, timeout после фактической записи и потерянный ответ; clock/lease, новый и повторный requestId, другая заявка того же email, consent transitions и late callback. Все email синтетические, тестовые API не выполняют внешних запросов.
5. Установить safe-log contract: допустимы environment, route, request correlation для внутреннего безопасного trace только если это не request credential, outcome code, duration и счётчики. Запрещены email, raw IP и HMAC IP, request/CRM ID, body, consent event properties, token, полный URL/query/referrer. Ошибка для пользователя и safe error code оператору — разные проекции.

**Артефакты:** типы/interfaces, config schema, fake CRM/analytics fixtures, безопасная таблица targets (пути: `src/domain/leads/`, `src/domain/measurement/`, `src/server/crm/`, `src/features/measurement/`; предложенные).

**DoD:** без credentials запускаются domain и fixture tests; невалидная конфигурация не выбирает иной environment; browser bundle не содержит server credentials; фикстуры не содержат реальных персональных данных. **Проверки:** Q12–Q16.

### LM-02 — Создать приватную lead-схему и миграции

**Этап:** прототип. **Зависимости:** LM-01, migration runner из FP-03. Grants окончательно применяются после появления таблиц.

1. Добавить версионированную SQL/Drizzle migration только для приватных lead-данных, совместимую с пустой базой и будущим кодом. Предлагаемая таблица `lead_requests` включает контрактные поля: `request_id UUID PRIMARY KEY`, `dedup_key` unique, `payload_hash`, `email`, `scenario` с CHECK enum, `contact_permission_version`, `contact_permission_at`, `created_at`, `updated_at`, `state` (`pending|accepted|failed`), `delivery_attempts`, nullable `lease_token`, `lease_until`, `crm_contact_id`, `safe_error_code`, `conversion_id UUID`, `expires_at`. `requestId` создаёт клиент для данной операции и валидирует сервер; отдельные `conversionId` и `leaseToken` создаёт сервер. Преобразовать имена в принятую SQL-конвенцию без потери совпадения с 09.
2. Случайный `requestId` — только credential операции, созданный клиентом и хранимый в памяти текущей вкладки; сервер валидирует его и создаёт отдельные `conversionId` и lease tokens. Canonical payload для `payloadHash` включает нормализованный email, `scenario` и `contactPermissionVersion`; `dedupKey` строится по нормализованным email + scenario, оба через HMAC-SHA256 и `LEAD_HMAC_SECRET`. Секрет или его производные не записывать в логи. Ограничить уникальность dedup `retained` строками: TTL cleanup должен удалить истёкшую запись после CRM cleanup, чтобы после фактического удаления допустить новую операцию.
3. Добавить ограничения целостности: поддерживаемое значение `scenario`; положительная версия permission; обязательный timestamp разрешения; `delivery_attempts` в допустимом диапазоне; accepted имеет стабильный `conversion_id`; `lease_token` и `lease_until` выдаются/снимаются совместно. `accepted` терминален. Не хранить текст заявки, имя или телефон.
4. Создать отдельную `lead_rate_limit_hits` (SQL-эквивалент таблицы `rate_limits` в 05/12) или эквивалентную нормализованную схему без raw IP: одна запись на попытку с `ip_hmac`, `occurred_at`, `expires_at`; индекс `(ip_hmac, occurred_at)` и индекс очистки по expiry. Реализовать атомарное окно «5 попыток за последние 10 минут» с сериализацией попыток одного HMAC-ключа, чтобы конкурентный запрос не обходил предел; raw IP не попадает даже во временную таблицу. Историю лимитов очищать по TTL 24 часа, не включать в backup.
5. После добавления lead-таблиц выдать web handler только необходимые операции над `lead_requests`/rate limits через `DATABASE_LEAD_URL`; `DATABASE_READ_URL` не получает даже `SELECT`, collector `DATABASE_IMPORT_URL` не читает и не пишет leads; migration/operator credential — только для схемы, backup и явно операторских процедур. Не считать app-level фильтр заменой SQL GRANT. Проверить позитивные и негативные GRANT на реальной временной PostgreSQL.
6. Реализовать runbook ротации `LEAD_HMAC_SECRET` без multi-key keyring: приостановить lead handler/maintenance; с migration/operator доступом в контролируемой транзакции пересчитать `dedup_key` и `payload_hash` всех retained rows из приватных email/scenario/permission version с новым secret; очистить `rate_limit_hits`; пока записи приостановлены, согласованно обновить server/operator secret config; проверить same-payload retry находит прежнюю строку, а changed payload отклоняется; затем возобновить обработчики. Пройти ротацию на изолированной БД; не выводить ни secret, ни производные ключи, фиксировать только безопасные counts/outcomes.

**Артефакты:** миграции и схема lead/private rate limit (предлагаемые пути: `migrations/*_lead_requests.sql`, `migrations/*_lead_rate_limits.sql`, `src/server/db/lead-repository.ts`), документированная procedure HMAC-secret rotation без значения секрета.

**DoD:** миграции с нуля и повторная проверка migration history работают; unique/constraint/clock cases подтверждены на PostgreSQL; две независимые DB-роли доказывают, что public/collector не могут читать leads, а lead writer не пишет snapshots; rate limit конкурентно не пропускает шестую попытку в скользящем окне; таблицы не попадают в fixtures/public read/backup snapshots. **Проверки:** Q13, Q17.

### LM-03 — Реализовать POST /api/leads, идемпотентность и lease

**Этап:** прототип. **Зависимости:** LM-02, интерфейсы LM-01; fake CRM достаточно.

1. Реализовать `POST /api/leads` на Node server runtime: same-origin JSON, body максимум 4 KB, `Origin` против environment `SITE_URL`, Zod/эквивалентная серверная schema и honeypot. Email trim/lowercase для dedup/CRM, проверить адрес длиной до 254 символов; `scenario` только `marketing_site|editorial_site|commerce_content`; контактное permission обязательно и unchecked по умолчанию на клиенте. Ошибка DB до контакта с Brevo возвращает 503.
2. Применять rate limit независимо от analytics consent. Сырой IP считывается только для HMAC в процессе запроса; он не сохраняется и не логируется. Honeypot отвечает внешне как accepted с `analyticsEligible:false`, не создаёт CRM запись, conversion ID или `lead_accepted`.
3. На submit клиент выдаёт UUID `requestId` и держит его только в памяти вкладки вместе с неизменяемым fingerprint отправленного payload. Повтор в той же вкладке использует тот же ID. Изменение email/scenario после неуспеха создаёт новый ID. Сервер повтор requestId с тем же `payloadHash` связывает с той же операцией; тот же ID с иным payload возвращает 409. Публичного GET по email/requestId и раскрытия foreign operation нет.
4. В короткой SQL-транзакции создать/найти операцию по request ID и dedup key. На каждую CRM попытку условным update выдать новый `leaseToken` и `leaseUntil = now + 30s`; зафиксировать транзакцию до сетевого вызова. При активной lease своего requestId вернуть 202 + `Retry-After`, без второго CRM вызова. Один HTTP submit — максимум один CRM request с таймаутом 10s; автоматического polling/retry/worker/outbox нет.
5. Финализировать результат условным update по тому же lease token. Поздний callback старого lease не может перезаписать новую попытку, а никакая ошибка после `accepted` не меняет terminal state. CRM network call не держит открытой SQL-транзакцию. После потери ответа/commit та же операция ждёт истечения lease, затем повторяет идемпотентный Brevo upsert с исходным email; accepted и `conversionId` возвращаются только после зафиксированного CRM success.
6. До 3 delivery attempts на операцию; при исчерпании только операторский `npm run leads:retry -- --env development --request-id UUID` после исправления config/schema сбрасывает cap по явному runbook. `DATABASE_LEAD_URL` обеспечивает web path; retry использует разрешённый operator lead-write target. Не печатать request credential в console/CLI output.
7. Ответы привести точно к 09: `200 accepted` только у собственного принятого requestId (тот же `conversionId` при retry), `202 pending` для собственной активной lease с задержкой повторной попытки, `400 invalid`, `409 changed payload`, `429` rate limit, `503` DB/CRM unavailable. Свой повтор принятой операции может вернуть `analyticsEligible:true`; другой `requestId` с уже существующим dedup key получает нейтральный accepted и `analyticsEligible:false`, без чужого `conversionId`/ID/статуса. Foreign pending отвечает нейтральным retryable состоянием, не подтверждая наличие контакта.
8. Для просроченной строки, которая ещё ждёт CRM deletion, не переиспользовать dedup key и не объявлять новую заявку. Удаление проекта из Brevo и DB идёт по LM-09; после успешного TTL-delete новая операция с тем же ключом разрешена.

**Артефакты:** API route, lead domain service/repository, injectable clock/lease, контракт ответов (предлагаемые пути: `src/app/api/leads/route.ts`, `src/server/leads/submit.ts`, `src/server/leads/lease-repository.ts`).

**DoD:** fake integration покрывает недоступную DB без CRM вызова, 5/10m rate cap, malformed/oversize/body origin, honeypot, concurrent duplicate IDs/keys, чужой pending/accepted, изменённый payload, 30s lease, 10s CRM timeout, 3-attempt cap, lost CRM response/DB commit, позднюю ошибку после accepted и stable conversionId. Ни в одном ответе/логе нет email, CRM contact ID или чужого request credential. **Проверки:** Q12, Q13, Q14, Q17.

### LM-04 — Реализовать Brevo Contacts adapter и модель обновления контакта

**Этап:** прототип. **Зависимости:** LM-01, LM-03; live smoke дополнительно зависит от FP-04.

1. Реализовать adapter только на сервере для Brevo Contacts API. Минимальный метод `upsert(email, scenario, permissionAt, requestId)` вызывает контактную операцию с `updateEnabled=true`, выделенным requests list и согласованными атрибутами `PKG_SCENARIO`, `PKG_CONTACT_PERMISSION_AT` (ISO) и `PKG_REQUEST_ID`. Передавать только нужные project fields.
2. Успех — только ожидаемый документированный 2xx от выбранной операции; проверить контракт API, ошибки и version/permissions при подключении FP-04. Не считать произвольный 400 или timeout дубликатом/success. Дубль существующего contact разрешать по реальной семантике Brevo upsert или явным разрешённым read/update шагом; результат должен быть наблюдаемым и безопасным, без второй записи в CRM.
3. Существующий Brevo contact — общий контакт, retained операции с разными scenarios живут в PostgreSQL; Brevo `PKG_*` поля отражают последнюю применимую retained заявку. Не включать кампании/automation, не отправлять письма, не снимать unsubscribe/blocklist и не добавлять пользователя в маркетинговую подписку.
4. Преобразовать 429/5xx/network/timeout и permanent auth/config/schema errors в safe failure, без утечки тела API. Lease повтор использует тот же payload и email; upsert безопасно переживает потерянный ответ. Число вызовов ограничено LM-03.
5. Добавить fake adapter fixtures на состояния API и contract test для фактических dev ответов. Credentials `BREVO_API_KEY` и list ID существуют отдельно для development/production, недоступны браузеру/CI untrusted PR и не выводятся в логах.

**Артефакты:** Brevo adapter и нормализатор безопасных ошибок (предлагаемые пути: `src/server/crm/brevo-contacts.ts`, `src/server/crm/brevo-errors.ts`), sanitized contract fixtures.

**DoD:** отдельный dev contact попадает только в requests list с правильными значениями; повтор не создаёт новый contact/CRM operation и не меняет unsubscribe/blocklist; API 2xx/duplicate/429/5xx/auth/timeout классифицируются согласно контракту, fake и live результаты указаны отдельно. **Проверки:** Q13, Q17.

### LM-05 — Собрать доступную форму и состояния заявки

**Этап:** прототип, прямой маршрут. **Зависимости:** LM-03; fake API подходит для первоначальной UI работы. Встраивание CTA в общий nav/footer координировать с CW, не блокировать вертикальный прототип.

1. Создать `/en/request-shortlist/` с заголовком/объяснением просьбы о помощи, email, enum `scenario`, обязательным unchecked contact-permission checkbox и privacy link. Нет имени, телефона, свободного текста, marketing opt-in или скрытого consent. Email не пишется в URL, localStorage, sessionStorage, PostHog или persistent client cache.
2. Реализовать доступные состояния `idle → submitting → accepted | retryable_error | validation_error | rate_limited`. Подписанные labels, связанные inline errors, keyboard focus и `aria-live`/status region; блокировка повторного submit пока запрос действительно в полёте, но навигация/форма не зависит от SDK и от аналитического consent.
3. После валидационной/временной ошибки сохранить значения в памяти компонента/вкладки; повторить тем же requestId, пока email и scenario не менялись. Ошибка от неизвестного outcome говорит «We could not confirm your request. Please retry.» и не симулирует success. Для активного 202 отобразить `Retry-After`/понятную задержку; не выполнять бесконечный polling.
4. Только подтверждённый 200 своего requestId показывает success «Your request is saved. The project owner may contact you about this request.»; визуально не обещать срок ответа/отправку письма. Чужой duplicate и honeypot не считать измеряемым accepted. Если событие имеет `analyticsEligible:false`, не выпускать `lead_accepted` даже при нейтральном accepted UI.
5. Связать CTA из формы с допустимым `entryPoint=nav|comparison|library|home`; значение задаёт внутренний UI enum, а не `Referer`/произвольный query. Вызовы `lead_form_viewed` проходят через consent-aware слой LM-07.

**Артефакты:** server-rendered form route и небольшие client form state/API adapter компоненты (предлагаемые пути: `src/app/en/request-shortlist/page.tsx`, `src/features/leads/shortlist-form.tsx`, `src/features/leads/api-client.ts`).

**DoD:** happy path, validation, unchecked permission, rate limit, pending, timeout/unknown, retry, changed payload и accepted duplicate визуально различимы; поля сохраняются при retry только в памяти; форма submit работает при `unknown`, `denied` и SDK failure; ошибки/status доступны keyboard/screen reader. **Проверки:** Q12, Q13, Q14, Q18.

### LM-06 — Реализовать consent state machine без раннего SDK

**Этап:** прототип. **Зависимости:** FP-02; параметры SDK и очистки сверяются по зафиксированной версии PostHog при FP-04.

1. Один consent controller предоставляет только `unknown|denied|granted`. До выбора, при отказе и после отзыва PostHog script не загружается и не инициализируется: нет analytics network requests, anonymous IDs, UTM persistence или experiment state. Экран выбора показывает равно доступные «Accept analytics» и «Reject analytics»; Privacy settings в footer/Privacy открывает изменение выбора без регистрации.
2. Consent cookie `consent_v1` на 180 дней содержит только выбор (`granted|denied`) и policy version; установить `Secure`, `SameSite=Lax` и `Path=/`. Так как это не секрет и privacy settings controller должен читать/менять значение, разрешить чтение этим controller либо обеспечить эквивалентный same-origin update path. Не хранить visitor ID, campaign, route или email. Не выдавать настройки cookie за заявление юридического соответствия.
3. При grant лениво загружать выбранный PostHog JS SDK и инициализировать ровно один раз на вкладку; отключить automatic pageviews, autocapture, session replay, surveys, feature flags/experiments и identify. Настроить EU ingestion host. Публичный HTML и CRM form должны работать даже если скрипт заблокирован или отклонён.
4. Защитить асинхронную загрузку от гонки: callback/init/capture заново проверяет текущее состояние consent непосредственно перед созданием/отправкой события. Выдавать generation token на consent lifecycle; смена на denied/withdraw инвалидирует pending callbacks, очищает внутреннюю очередь и не даёт опоздавшему import/init запустить SDK или capture.
5. При withdraw сначала синхронно перевести состояние в denied, остановить capture, очистить SDK persistence/anonymous ID известные cookies и localStorage keys выбранной версии, а также session attribution и conversion dedupe state; сохранить только consent cookie. Не отправлять прошлые события при последующем grant. Детали disable/reset/clear API и storage keys подтвердить по lockfile и network/storage smoke, не полагаться на defaults.
6. Локально держать сенсор событий/состояние; не передавать email, HMAC или requestId в `identify`. Если пользователь даёт согласие на уже открытой странице, по 10 §2 разрешить однократный `page_viewed` для текущей страницы, затем продолжить tracking переходов. Не воспроизводить события предыдущих маршрутов и не отправлять задним числом `comparison_viewed` для сравнения, открытого до grant; событие сравнения возникает только при post-grant открытии.

**Артефакты:** единый consent store/controller, banner/dialog/privacy settings, PostHog lazy loader и очистка (предлагаемые пути: `src/features/measurement/consent-store.ts`, `src/features/measurement/consent-ui.tsx`, `src/features/measurement/posthog-client.ts`).

**DoD:** network/storage evidence показывает ноль SDK загрузок, событий, anonymous ID и optional storage до grant; grant создаёт один SDK; deny оставляет SDK отсутствующим; withdrawal очищает согласованные keys и сохраняет только denied policy cookie; reload в denied остаётся без SDK; late callback после withdrawal не вызывает capture/init; grant на уже открытой странице отправляет не более одного текущего `page_viewed`, но не переигрывает прошлые route/comparison events. **Проверки:** Q14, Q15, Q16, Q18.

### LM-07 — Добавить event allowlist, атрибуцию и accepted funnel

**Этап:** прототип. **Зависимости:** LM-03 (accepted API result), LM-05 (form/navigation), LM-06 (consent gate), FP-02.

1. Описать один типизированный event map с runtime schema validation. Common fields: `eventSchemaVersion=1`, `environment=development|production`, `routeType`, опциональный собственный стабильный `entityId`, `locale=en`, `occurredAt`, случайный `eventId`. `routeType` только `home|catalog|library|comparison|methodology|lead_form|privacy`; ID — allowlisted catalog identity.
2. Разрешённые события: `page_viewed` только на новой навигации после consent; `comparison_viewed` при открытии опубликованной пары; `official_resource_clicked` с `libraryId` и `resourceType=docs|website`; `lead_form_viewed` с `entryPoint=nav|comparison|library|home`; `lead_accepted` после 200 accepted своего requestId, только если сервер вернул `analyticsEligible:true` и consent ещё granted. Не определять submit как conversion.
3. Запретить любые неизвестные properties на client и `before_send`; выключить/санитизировать автоматические URL/referrer properties. Не передавать email/email hash, IP, requestId, CRM ID, `conversionId` до accepted, form values кроме enum scenario, user search query `q`, полный URL/query, referrer URL и произвольный текст ошибки. `conversionId` — отдельный случайный UUID операции, не request credential.
4. При `lead_accepted` положить `conversionId` в event payload и детерминированно использовать его как `eventId`; при повторе accepted собственного ID событие не должно плодить уникальные конверсии. Список уже отправленных conversion IDs хранить в sessionStorage только при grant (fallback — память вкладки); очистить его на withdrawal. Сетевые дубли допустимы, аналитический запрос агрегирует уникальный conversionId; exactly-once delivery не обещать.
5. Собирать UTM только после явного grant и только из текущего URL. Нормализовать комбинацию `utm_source/medium/campaign` в allowlist `portfolio|demo`, сохранять только `campaignKey` в sessionStorage до закрытия вкладки и прикреплять только к разрешённым event properties. Неизвестные и произвольные raw UTM отбрасывать; до согласия не сохранять и не восстанавливать их позже.
6. Настроить dashboard запросы: (а) volume — уникальный `conversionId`; (б) comparison funnel — уникальные consenting anonymous visitors с `comparison_viewed`, формой `lead_form_viewed` и qualifying `lead_accepted` по тому же anonymous distinct_id в течение 7 суток; rate numerator — visitors с accepted после comparison, denominator — уникальные visitors с comparison_viewed. Nav/home заявки отображать отдельно и не помещать в comparison numerator без comparison touch. Контрактное окно и counts сверить с 10 §3.
7. Показать различие с operational count: SQL `accepted` rows/операционная CRM заявка — приватная система учёта; PostHog отражает только посетителей, согласившихся и фактически отправивших событие. Не связывать anonymous ID и email/request row и не выдавать разницу counts за дефект/погрешность.

**Артефакты:** event map/schema, consent-aware tracker, funnel/volume dashboard definitions и безопасные synthetic query fixtures (предлагаемые пути: `src/features/measurement/events.ts`, `src/features/measurement/tracker.ts`, `docs/analytics-dashboard.md`).

**DoD:** неизвестное свойство отклоняется runtime-схемой; synthetic events доказывают отсутствия PII/query/referrer и raw UTM, allowlist campaign работает только при grant; дубли route/event и accepted retries сводятся к одному unique conversion; окно и numerator/denominator dashboard совпадают с 10; fixture показывает отдельный nav/home поток и несходство operational/analytics totals без backfill. **Проверки:** Q14, Q15, Q16.

### LM-08 — Пройти независимый вертикальный прототип формы и измерения

На выделенных **development** targets провести один безопасный собственный тестовый lead alias владельца: правильный Brevo requests list/attributes, accepted ответ только на реальный CRM success, повтор той же операции, dedup и очистка тестовой операции. ### LM-09 — Ввести TTL, CRM deletion, private backup и восстановление

**Этап:** до production release. **Зависимости:** LM-02–LM-04, FP-03 roles/backup access; совместная rehearsal с QA-04.

1. Реализовать lead-cleanup как отдельный шаг единого запланированного `npm run maintenance -- --env <env>` из 12, с явным dry-run/apply и отдельным least-privilege lead credential/lease. Не добавлять вторую общую maintenance команду и не вызывать cleanup из public route. DP-владелец поставляет собственный snapshot cleanup шаг/lock/credential в общем расписании; lead cleanup никогда не использует collector rights. Leads: 30 дней после `createdAt`; CRM project contact/attributes очищаются после истечения последней retained операции; rate-limit HMAC hits — 24 часа; PostHog retention — 90 дней в account settings, а при недоступности настройки до запуска проверить ежемесячный delete path. Не сохранять raw provider payload.
2. Порядок удаления lead обязателен: выбрать только due row(s); сначала согласовать project state в Brevo, затем удалить DB rows. При сбое CRM оставить приватную DB row как retry marker и повторить в следующем maintenance run; не терять запись раньше внешней очистки. Работать серийно в dev smoke; production schedule — daily после release.
3. Shared contact поведение: если у того же email есть другая retained заявка, не удалять contact/list membership; обновить `PKG_*` attributes по последней retained заявке и удалить только истёкшую row. Если retained заявок больше нет — удалить только project list membership/`PKG_*` attrs; если contact принадлежит только PkgCompass, удалить контакт согласно проверенному Brevo API. Чужие списки/назначения/непроектные attributes не удалять. При конфликте с конкурентной заявкой очистка не должна стереть её свежий state: сериализовать операторскую процедуру по нормализованному contact key короткой DB lease/claim либо доказать эквивалентную защиту; CRM network не выполняется под открытой транзакцией. Не строить общий job framework.
4. При операторском удалении по privacy request применять тот же путь, покрывать все retained lead rows, contact/list/attributes и не печатать email в отчёте. Сверить, что обязательное разрешение на контакт не является разрешением на newsletter.
5. Держать отдельный daily encrypted backup private lead state с окном 7 дней в закрытом operator storage; ключ отдельно, не в public CI artifacts. Сохранять accepted/dedup/permission/lease state для корректного восстановления, не включать 24-hour rate-limit history. SQL snapshot/content backup — отдельный без PII контур. Настроить только существующий CLI/runbook интерфейс 12, не считать Neon branch резервной копией.
6. В изолированном restore rehearsal остановить handler, восстановить private schema/data, проверить accepted rows и стабильные conversion IDs; сбросить просроченные delivery leases и удалить все expired rows из Brevo/DB до включения handler. Проверить CRM deletion/retry на fake adapter; real CRM update/delete smoke — только в dev list с alias владельца. Проверить role isolation после restore.
7. После удаления expired row dedupKey освобождается и новая заявка с теми же email/scenario создаёт новую операцию и новый `conversionId`; pending удаления или неуспешный CRM delete сохраняет row и не выпускает новый accepted. Документировать безопасные retry шаги, credential target, состояние и cleanup evidence без PII.

**Артефакты:** maintenance CLI, CRM delete/attribute reconciliation, daily encrypted backup/restore runbook и закрытая sanitized rehearsal record (предлагаемые пути: `scripts/maintenance-leads.ts`, `scripts/backup-leads.ts`, `scripts/restore-leads.ts`, расширение `src/server/crm/brevo-contacts.ts`).

**DoD:** retention/deletion выполняются по 30d/24h/7d/90d контрактам; CRM delete идемпотентен и не портит shared contact; ошибка внешнего удаления сохраняет row для повтора; dry-run не мутирует DB/CRM; encrypted backup реально восстановлен в изоляции, принятые заявки/permission/dedupe state сохранены, expired requests очищены до включения; `DATABASE_READ_URL`/collector role после restore не получают leads. **Проверки:** Q13, Q17.
