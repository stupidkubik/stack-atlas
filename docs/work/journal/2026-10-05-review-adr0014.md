# Проверка упрощений ADR 0014: замечания для реализации

Дата: 5 октября 2026. Источник — ревью незакоммиченных изменений после принятия [ADR 0014](../../decisions/0014-learning-project-simplifications.md), относительно базового commit `6be4438`.

Это очищенная долговременная сводка ревью, а не новый контракт или отчёт готовности приложения. Спецификации и код не исправлялись. Реализационные задачи не закрыты. Ни один из приведённых ниже сценариев приложения пока не проверен на работающем проекте.

## Вывод и статусы

Упрощения можно сохранить: опубликованный AI-review читается из Sanity, метрики хранят текущее состояние, email находится только в Brevo. Замечания не требуют возвращать историю метрик, бэкап заявок или полную систему delivery leases.

## R01 — Accepted должен быть терминальным

Источник: [09 §3](../../09-lead-form.md), шаг 5; [LM-03](../../plans/04-leads-consent-and-measurement.md). При ошибке указан безусловный переход в failed, хотя конкурентные запросы одного requestId разрешены.

**Будущая проверка:** на PostgreSQL и управляемом fake CRM запустить два запроса одной операции. Задержать ответ второго. Первый завершить успешно и дождаться accepted в БД; второй завершить timeout/ошибкой. Затем повторить исходную операцию и отправить дубликат с новым ID.

**Ожидаемый результат:** accepted не откатывается; повтор исходной операции возвращает прежний conversionId; новая операция того же email/scenario не создаёт вторую eligible-конверсию в пределах срока дедупликации.

**Минимальное направление исправления:** условные переходы всех состояний, включая failed, и чтение результата конкурентного завершения. Lease сам по себе не обязателен. Отдельно проверить обратный порядок ответов и два успешных ответа.

## R02 — Очистка и upsert должны быть согласованы

Источник: [09 §5](../../09-lead-form.md), правило Brevo TTL; [LM-09](../../plans/04-leads-consent-and-measurement.md), шаг 2.

**Будущая проверка:** maintenance выбирает просроченный контакт и останавливается перед изменением CRM. Отправить новую заявку, дождаться успешного upsert и accepted. Продолжить maintenance. Повторить для контакта только в проектном списке и для контакта с другими списками.

**Ожидаемый результат:** свежий контакт, проектное членство и актуальные PKG-атрибуты сохраняются. Успешная новая заявка не теряется из-за старого списка кандидатов на очистку.

**Минимальное направление исправления:** согласование upsert и удаления одного контакта через общую блокировку либо проверенный механизм условного удаления. Одно повторное чтение перед удалением оставляет окно гонки. Проверить механизм на выбранных DB/CRM adapters; fake доказывает порядок операций, live dev smoke — доступность нужных API.

## R03 — Одинаковое правило для TTL и ручного удаления

Источник: [09 §5](../../09-lead-form.md), операторское удаление; [LM-09](../../plans/04-leads-consent-and-measurement.md), шаги 2 и 4. TTL учитывает другие списки, а ручной путь предписывает удалить контакт целиком.

**Будущая проверка:** подготовить synthetic контакт с проектным и сторонним списками, непроектными атрибутами. Выполнить TTL и операторское удаление отдельно. Дополнительно проверить контакт только в проектном списке, но с другим назначением.

**Ожидаемый результат:** удалены только проектное членство, PKG-атрибуты и проектные строки; сторонние данные сохранены. Полное удаление разрешено только при доказанной принадлежности контакта исключительно проекту. Единственный список не является достаточным доказательством.

**Минимальное направление исправления:** один общий путь удаления для TTL и оператора; явный критерий принадлежности либо изолированное проектное CRM-окружение. Live проверки — только на принадлежащих владельцу dev fixtures, без чужих контактов.

## R04 — Удаление после ротации HMAC

Источник: [09 §5](../../09-lead-form.md), ротация LEAD_HMAC_SECRET и удаление по HMAC.

**Будущая проверка:** создать synthetic строки для каждого сценария старым ключом, сменить ключ, затем выполнить удаление для того же synthetic адреса.

**Ожидаемый результат:** старые retained строки удалены по заявленному операторскому процессу. Допустимость дополнительной конверсии после ротации не решает задачу удаления старых строк.

**Минимальное направление исправления:** очищать lead_requests при ротации либо сохранять предыдущий ключ на ограниченный срок для удаления. Уточнить выбранное поведение в runbook; email в БД не добавлять.

## R05 — Evidence обязателен для Q-gates

Источник: [work/README](../README.md) и [worklog.py](../../../scripts/worklog.py). Документ требует evidence при --gate Qxx; скрипт проверяет файл только при переданном --evidence.

**Выполненная проверка:** в disposable directory через fixture из tests/tooling/test_worklog.py выполнены start → check(pass, --gate Q01, без --evidence) → finish(verified, --dod-confirmed). Получен manifest с gate Q01, evidence null и status verified. Реальная доска задач не изменялась.

**Критерий исправления:** check с Q-gate без существующего evidence отклоняется; обычный check без gate допускается; корректный Q-gate с evidence допускается. Проверить также завершение ранее сохранённого run с Q-gate без evidence — оно не должно обходить новое правило.

## Evidence и закрытие замечаний

На момент ревью: `git diff --check` — pass; `python3 -m unittest discover -s tests/tooling -v` — pass, 6 тестов. Эти результаты проверяют tooling и формат diff, а не корректность контрактов приложения. Воспроизведение R05 подтверждает отдельный пробел, который существующие тесты не покрывают.

При проверке реализации сохранить очищенные результаты в artifacts/runs/<run-id>/ и зарегистрировать их через worklog для соответствующей задачи. Для R01–R02 нужны воспроизводимые тесты с управляемым порядком операций; для R03–R04 — assertions по сохраняемым и удаляемым данным. Не включать реальные email, request credentials, ключи или raw CRM payload.

Закрывать каждый Rxx отдельно: записать выбранное исправление, commit реализации, выполненную проверку, относительный путь к evidence и итог. До выполнения сценария статус остаётся открытым; изменения текста документации сами по себе не являются runtime pass.
