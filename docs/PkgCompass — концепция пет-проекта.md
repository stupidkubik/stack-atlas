## Кратко

PkgCompass — публичный мультиязычный каталог и сравнение JS/TS-библиотек: живые метрики из npm и GitHub, редакционный контент в Sanity, полноценный маркетинговый слой. Срок — 3–5 дней с AI-агентами.

Цель проекта — закрыть в портфолио разрыв между «Junior Frontend с приложениями» и нишей Frontend / Web Engineer (Marketing & Digital Experience). Сейчас все пет-проекты — приложения: магазин, канбан, дашборд. PkgCompass станет первым контентно-маркетинговым проектом и покажет headless CMS, техническое SEO, локализацию контента, аналитику, лид-форму с CRM, A/B-тест и агентные workflow с контролем.

Проект одновременно работает на обычные frontend-вакансии: Next.js App Router, Server Components, кеширование, фасетный поиск, доступность и тесты остаются в ядре.

## Концепция продукта

Разработчик заходит на PkgCompass, чтобы выбрать библиотеку под задачу и понять, когда она подходит, а когда нет. Каталог охватывает 60–100 библиотек в 8–10 категориях: state management, формы, валидация, data fetching, тестирование, анимации, UI-киты, headless CMS, i18n, роутинг.

Каждая библиотека состоит из двух слоёв:

- **Живые метрики** из внешних API: недельные загрузки и тренд, звёзды, дата последнего релиза, открытые issues, лицензия, число зависимостей.
- **Редакционный слой** в Sanity: описание, «когда выбирать / когда не выбирать», плюсы и минусы, альтернативы, FAQ, переводы на три языка.

Типы страниц: главная из секций, страница категории, страница библиотеки, страница сравнения двух библиотек, лендинг подписки на еженедельный дайджест.

### Почему эта тема

- **Реальные данные и реальный трафик.** Сайт можно запустить публично, это сильнее вымышленной SaaS-компании.
- **Маркетинговый слой органичен.** Каталог и сравнения — классическое programmatic SEO, подписка — лид-форма, CTA подписки — объект A/B-теста.
- **Домен знаком тебе.** Редакционный контент пишется быстро и без натяжек.
- **Домен знаком интервьюеру.** Он сам выбирает библиотеки, поэтому разговор о проекте завязывается сразу.

Альтернативы, если тема не зайдёт: агрегатор IT-конференций на публичных API или мультиязычный гид по городу на OpenStreetMap и Wikidata. Обе слабее по programmatic SEO и дальше от интересов интервьюеров.

Каталоги и сравнения npm-пакетов уже существуют, поэтому PkgCompass выигрывает не новизной продукта, а углом — оценкой AI-readiness библиотек — и архитектурой как предметом демонстрации.

Выводы для проекта:

- **Трафик не обещать.** По запросам «X vs Y» уже ранжируются PkgPulse и npm-compare. Цель — архитектура, а не позиции в поиске.
- **Главное отличие — AI-readiness.** Публичного каталога, который оценивает, насколько библиотека удобна для работы с coding-агентами, в поиске не нашлось. Подробности — в следующем разделе.
- **Рамка каталога — инструменты для контентных и маркетинговых сайтов:** headless CMS, i18n, формы, аналитика, изображения, SEO. Это напрямую поддерживает позиционирование из рыночного отчёта.
- **Мультиязычность — техническая демонстрация,** а не продуктовое преимущество: разработчики в основном ищут на английском.

Фраза для README: «PkgCompass не конкурирует с npmtrends и PkgPulse. Это референсная архитектура контентной платформы, а её продуктовая особенность — оценка того, насколько библиотека готова к разработке с AI-агентами».

### Честная методология

Оценка отвечает на вопрос «что библиотека предоставляет агентам», а не «насколько хорошо агенты пишут с ней код». Это нужно написать прямо на сайте, потому что эффективность части сигналов не доказана:

- **llms.txt** — предложенный, а не принятый стандарт. Ahrefs отмечает, что ни один крупный провайдер LLM официально его не поддерживает и доказательств пользы пока нет ([Ahrefs](https://ahrefs.com/blog/what-is-llms-txt/)). Поэтому вес у сигнала средний, а не максимальный.
- **AGENTS.md** адресован агентам контрибьюторов, а не пользователей библиотеки. Отсюда минимальный вес и отдельная пометка «для контрибьюторов». Замеры Agentic AI Foundation показывают неоднозначный эффект: на одной задаче прогон с файлом оказался медленнее и дороже ([AAIF](https://aaif.io/blog/measuring-agents-md-what-five-runs-show-that-one-doesn-t)).
- **Context7** требует ключ, и перед публикацией его данных нужно проверить условия использования. Если показывать нельзя — сигнал убирается, веса пересчитываются.

На карточке показывается не только итоговое число, но и разбивка по сигналам со ссылкой на доказательство (URL файла, запись в реестре) и датой проверки. Страница методологии живёт в Sanity и версионируетсdя: при изменении весов старые оценки помечаются версией формулы.

### Как это ложится на архитектуру

- **Новый тип документа `aiReadinessSnapshot`** рядом с `metricsSnapshot`: значение каждого сигнала, URL доказательства, источник, дата, статус `auto` или `confirmed`, версия формулы.
- **Коллектор в том же cron**, что и метрики: раз в неделю, а не ежедневно — сигналы меняются редко.
- **Сопоставление MCP-серверов и skills неточное:** поиск по имени даёт ложные совпадения. Совпадения ниже порога уверенности уходят в очередь AI-аудитора: агент предлагает «это официальный сервер zod?», человек подтверждает. Это даёт агентному workflow реальную, а не придуманную задачу.
- **Ручное переопределение:** редактор может исправить сигнал с обязательным полем «причина», и это видно в истории.

### Интерфейс

- Бейдж оценки на карточке и разбивка по сигналам на странице библиотеки.
- Фильтры каталога: «есть MCP-сервер», «есть llms.txt», «встроенные типы».
- Строка AI-readiness в таблице сравнения двух библиотек.
- Лендинг «Самые AI-ready библиотеки по категориям» — хороший кандидат для индексации и для дайджеста.
- Новые события аналитики: `ai_filter_used`, `ai_breakdown_opened`, `methodology_viewed`.

### PkgCompass сам должен быть AI-ready

Сайт, который оценивает AI-readiness, обязан сам её демонстрировать. Это одновременно сильный пункт для маркетинговых вакансий, где всё чаще спрашивают про видимость в AI-поиске:

- `/llms.txt` и `/llms-full.txt`, сгенерированные из Sanity при публикации.
- Markdown-версии страниц библиотек по адресу `.../zustand.md`.
- Публичный JSON-эндпоинт с оценками и методологией.

### Что меняется в плане

Фича добавляет примерно полдня-день. Коллекторы сигналов типов, llms.txt и MCP Registry — в день 1 вместе с импортом. Бейджи, фильтры и страница методологии — в день 2. Очередь подтверждений для аудитора — в день 4.

Если время поджимает, первыми режутся Context7 и AGENTS.md, затем agent skills. Типы, llms.txt и MCP-сервер — минимальное ядро фичи: все три открытые и не требуют ключей.

Строка для резюме дополняется: «оценка AI-readiness библиотек по открытым данным (npm, MCP Registry, llms.txt) с прозрачной методологией и подтверждением неточных совпадений через AI-агента с ручным одобрением».

## Источники данных

Метрики берутся из трёх бесплатных публичных API и никогда не запрашиваются из браузера посетителя: сервер забирает их по расписанию и кеширует.

| API                                                                                    | Что берём                                                        | Ограничения и заметки                                           |
| -------------------------------------------------------------------------------------- | ---------------------------------------------------------------- | --------------------------------------------------------------- |
| [npm downloads API](https://github.com/npm/registry/blob/main/docs/download-counts.md) | Загрузки за неделю, дневной ряд за 12 месяцев для графика тренда | Без ключа; поддерживает пакетные запросы для нескольких пакетов |
| [npm registry](https://github.com/npm/registry/blob/main/docs/REGISTRY-API.md)         | Последняя версия, дата релиза, лицензия, ссылка на репозиторий   | Без ключа; ответ для старых пакетов бывает большим              |
| [GitHub REST API](https://docs.github.com/en/rest)                                     | Звёзды, открытые issues, дата последнего коммита, топики         | Нужен токен: без него лимит слишком мал для 100 репозиториев    |
| [deps.dev API](https://docs.deps.dev/)                                                 | Число зависимостей, лицензии, OpenSSF Scorecard                  | Без ключа; хороший источник для блока «здоровье пакета»         |

Лимиты и форматы ответов перед стартом стоит сверить с документацией: они меняются, а значения здесь приведены по памяти.

### Как данные попадают на сайт

1. **Первичный импорт.** Скрипт создаёт в Sanity документы библиотек по списку пакетов (`seed.json`): название, npm-имя, репозиторий, категория.
2. **Метрики.** Ежедневный cron (Vercel Cron или GitHub Actions) запрашивает API и пишет снимок метрик в отдельный тип документа `metricsSnapshot`, а не в редакционный документ библиотеки.
3. **Обновление страниц.** После записи снимков скрипт вызывает `revalidateTag('metrics')`, страницы пересобираются без полного деплоя.

Разделение редакционного контента и метрик — одно из ключевых архитектурных решений: робот не перезаписывает текст редакторов, а история метрик хранится отдельно.

## Архитектура и стек

Sanity — единственный источник правды: в него пишут редакторы, робот импорта и AI-аудитор, а Next.js только читает и отдаёт страницы.

Каждый писатель в Sanity имеет свой тип документов и свои права: робот пишет только снимки метрик, агент — только черновики, публикует человек. Конверсия засчитывается с сервера, а не из браузера.

| ------------------ | ------------------------------------- | ---------------------------------------------------------------------- |
| Фреймворк          | Next.js App Router, TypeScript strict | Якорь трудоустройства из отчёта; Server Components, ISR, metadata API  |
| CMS                | Sanity                                | Бесплатный тариф, схемы в коде, visual editing, мощный API для агентов |

## Контентная модель Sanity

Модель строится на ссылках между документами, а не на больших JSON-блобах страниц: так редактор меняет категорию или автора в одном месте, и это отражается везде.

| Тип документа     | Ключевые поля                                                                                                    | Ссылается на                         |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| `library`         | Название, npm-имя, репозиторий, логотип, описание, «когда выбирать / не выбирать», плюсы и минусы, FAQ, SEO-поля | `category`, `library` (альтернативы) |
| `category`        | Название, slug, описание, порядок                                                                                | —                                    |
| `comparison`      | Пара библиотек, редакционный вердикт, таблица критериев, флаг `indexable`                                        | `library` × 2                        |
| `metricsSnapshot` | Дата, загрузки, звёзды, issues, последний релиз                                                                  | `library`                            |
| `page`            | Slug, массив секций (page builder), SEO-поля                                                                     | Секции                               |
| `redirect`        | Откуда, куда, код 301/308                                                                                        | —                                    |
| `siteSettings`    | Навигация, футер, дефолтные SEO-поля, OG-шаблон                                                                  | —                                    |

Секции page builder: hero (с вариантами для A/B), сетка категорий, растущие библиотеки, блок подписки, FAQ, текстовый блок на Portable Text. Каждая секция имеет ограничения: например, hero допускает максимум 2 CTA, заголовок до 70 символов.

### Локализация в схеме

Используется **локализация на уровне полей** (field-level) для `library`, `category` и `comparison`: один документ, переводимые поля хранятся по локалям. Для `page` — **локализация на уровне документов**: каждая языковая версия отдельным документом, связанным через плагин document internationalization. Это позволяет немецкой версии лендинга иметь свою структуру секций.

Выбор двух подходов в одном проекте — хороший материал для ADR: field-level проще для однородных данных, document-level гибче для маркетинговых страниц.

### Валидация и редакторский опыт

- Обязательные SEO-поля с предупреждением о длине: title до 60 символов, description до 160.
- Обязательный alt для изображений.
- Уникальный slug в пределах локали.
- Preview в Presentation tool: редактор видит черновик прямо на сайте до публикации.

## SEO и локализация

Главное SEO-решение проекта — явная политика индексации: в поиск попадают только страницы с редакционной ценностью, автогенерированные получают noindex.

### Локали и маршрутизация

- Три локали: `en` (по умолчанию), `de`, `es`. Выбраны под глобальную удалёнку: английский плюс два крупных европейских рынка.
- Маршруты с префиксом: `/en/libraries/zustand`, `/de/bibliotheken/zustand`. Сегменты пути переводятся, slug библиотеки остаётся npm-именем.
- Корень `/` определяет язык по `Accept-Language` в middleware и делает редирект, но с возможностью вручную выбрать язык через cookie.
- Fallback: если перевод страницы библиотеки отсутствует, страница в этой локали не создаётся и не попадает в sitemap. Подставлять английский текст под немецким URL нельзя — это дубль контента.

### Метаданные и разметка

- `generateMetadata` на каждом типе страниц: title, description, canonical, `alternates.languages` для hreflang, включая `x-default`.
- Canonical всегда указывает на саму страницу в её локали, а не на английскую версию.
- JSON-LD: `SoftwareApplication` для библиотеки, `ItemList` для категории, `BreadcrumbList` везде, `Organization` и `WebSite` на главной.
- Динамические OG-картинки через `next/og`: название, категория, загрузки за неделю.
- Sitemap index с отдельной картой на локаль, `lastmod` из `_updatedAt` документа.
- `robots.ts`: закрыты preview-маршруты, API и страницы поиска с параметрами.
- Редиректы из документов `redirect` в Sanity применяются в middleware.

### Политика индексации сравнений

Для 80 библиотек в 10 категориях можно сгенерировать около 300 пар внутри категорий. Если все они будут шаблонным текстом с цифрами, это doorway-страницы, которые вредят сайту.

| Тип сравнения                                | Индексация      | Sitemap |
| -------------------------------------------- | --------------- | ------- |
| С редакционным вердиктом (`indexable: true`) | index           | Да      |
| Автогенерированное, только метрики           | noindex, follow | Нет     |
| Пара из разных категорий                     | Не генерируется | —       |

Раздел о политике индексации в README — то, что отличает проект от типичного junior-портфолио: он показывает понимание разницы между programmatic SEO и спамом.

## Маркетинговый слой

Маркетинговый слой строится вокруг одной конверсии — подписки на еженедельный дайджест растущих библиотек. Всё остальное (события, эксперимент, CRM) работает на измерение и улучшение этой конверсии.

### Аналитика

Все события описаны в одном файле со схемами Zod и отправляются через единый адаптер `track()`. Прямых вызовов `gtag()` или `posthog.capture()` в компонентах нет.

| Событие                    | Когда срабатывает              | Свойства                        | Зачем                      |
| -------------------------- | ------------------------------ | ------------------------------- | -------------------------- |
| `library_viewed`           | Открыта страница библиотеки    | `library`, `category`, `locale` | Популярность контента      |
| `comparison_viewed`        | Открыто сравнение              | `pair`, `indexable`             | Ценность сравнений         |
| `search_used`              | Применён фильтр или поиск      | `query_length`, `filters`       | Качество каталога          |
| `outbound_clicked`         | Клик на npm, GitHub или docs   | `library`, `target`             | Полезность страницы        |
| `subscribe_form_started`   | Первое взаимодействие с формой | `placement`, `variant`          | Начало воронки             |
| `subscribe_form_submitted` | Сервер подтвердил подписку     | `placement`, `variant`, `utm_*` | Основная конверсия         |
| `experiment_exposed`       | Вариант hero реально показан   | `experiment`, `variant`         | Знаменатель A/B-теста      |
| `locale_changed`           | Ручная смена языка             | `from`, `to`                    | Качество определения языка |

Инструмент — PostHog: бесплатный тариф покрывает product analytics, feature flags и эксперименты в одном месте. Адаптер позволяет параллельно отправлять события в GA4 через GTM, что стоит показать как опцию.

Правила, которые стоит отразить в README:

- `subscribe_form_submitted` отправляется **с сервера** после успешной записи, а не по клику. Иначе ошибки и спам засчитаются как конверсии.
- Consent: до согласия аналитика работает в cookieless-режиме или не загружается вовсе, после согласия — полноценно. Поведение описано явно.
- UTM-параметры сохраняются в first-party cookie при первом визите и передаются в CRM вместе с подпиской.
- Реальные Core Web Vitals (LCP, INP, CLS) собираются библиотекой `web-vitals` и отправляются тем же адаптером.

### Форма → CRM

1. Форма на React Hook Form с той же Zod-схемой, что и на сервере.
2. Server action проверяет honeypot-поле и время заполнения.
3. Rate limit по IP через Upstash Redis.
4. Повторная валидация на сервере.
5. Запись в CRM через интерфейс `CrmAdapter` с двумя реализациями: HubSpot Free или Brevo и мок для тестов.
6. При ошибке CRM — одна повторная попытка, затем запись в очередь неудачных отправок и структурированный лог.
7. Серверное событие `subscribe_form_submitted` с `utm_*` и вариантом эксперимента.
8. Письмо-подтверждение (double opt-in) через Resend.

Идемпотентность: повторная отправка того же email обновляет контакт, а не создаёт дубль.

### A/B-эксперимент

- **Гипотеза:** hero с конкретной выгодой («5 растущих библиотек каждый понедельник, 2 минуты чтения») конвертирует лучше общего («Будь в курсе экосистемы JS»).
- **Единица назначения:** анонимный посетитель, вариант закреплён в cookie на 30 дней.
- **Назначение:** в middleware, до рендера, чтобы не было мерцания контента.
- **Exposure:** событие отправляется, только когда hero попал в видимую область.
- **Метрика:** доля `subscribe_form_submitted` от `experiment_exposed`.
- **Одна переменная:** меняется только текст заголовка. CTA, цвет и картинка одинаковы, иначе результат не интерпретировать.

На учебном трафике статистической значимости не будет, и это нормально. В README достаточно показать расчёт нужного размера выборки и честно написать, что вывод делать рано.

## AI-агенты и автоматизация

В проекте два агентных workflow, и в обоих LLM только предлагает изменения, а применяет их детерминированный код после одобрения человеком.

### Агент-аудитор контента

1. Скрипт выгружает документы из Sanity и детерминированно находит проблемы: пустые переводы, title длиннее 60 символов, пустой alt, битые внешние ссылки, библиотеки без альтернатив.
2. LLM получает список проблем с контекстом и возвращает предложения исправлений в структурированном JSON по Zod-схеме.
3. Предложения валидируются схемой и записываются в отчёт: документ, поле, было, предлагается, причина.
4. Человек одобряет или отклоняет каждое предложение (CLI-интерфейс или отдельная страница в Sanity Studio).
5. Одобренные правки применяются через Sanity mutations с `ifRevisionId` — если редактор успел изменить документ, патч не применится.
6. Правки пишутся в черновик, а не в опубликованную версию. Публикует человек.

### Дайджест в n8n

1. Cron по понедельникам.
2. Запрос снимков метрик за неделю, расчёт роста загрузок.
3. Топ-5 растущих библиотек передаются в LLM для короткого описания.
4. Черновик дайджеста отправляется в Telegram с кнопками «Отправить» и «Отклонить».
5. Только после подтверждения — рассылка подписчикам через Resend или Brevo.

### Границы безопасности

| Компонент     | Права                                                        | Почему                                          |
| ------------- | ------------------------------------------------------------ | ----------------------------------------------- |
| Агент-аудитор | Чтение Sanity, запись только в черновики после одобрения     | Опубликованный контент меняет человек           |
| n8n           | Чтение метрик, отправка только после подтверждения           | Рассылку нельзя отозвать                        |
| Токены        | Отдельный Sanity-токен с минимальными правами, секреты в env | Утечка не даёт полного доступа                  |
| Внешний текст | Описания из npm и GitHub считаются данными, не инструкциями  | Защита от prompt injection через README пакетов |

Последний пункт стоит подчеркнуть на собеседовании: README пакета — неконтролируемый текст, и агент, который его читает, может получить в нём инструкции. Это реальный вектор атаки, о котором пишут исследования 2026 года.

### Агент в процессе разработки

Основной инструмент — один coding-агент (Claude Code или Codex). Правило проекта: агент пишет код, но любая найденная им в исследовательском QA проблема превращается в детерминированный Playwright-тест, который навсегда остаётся в CI. Playwright MCP используется для исследования, не как замена тестам.

Тесты проверяют не только UI, но и маркетинговые контракты: события, метаданные, редиректы и миграции. Именно это отличает проект от обычного frontend-портфолио.

| Уровень            | Инструмент            | Что проверяет                                                                                                                |
